# Mobile App via PWA + Trusted Web Activity — Design

**Date:** 2026-07-19
**Status:** Approved
**Goal:** Get revision_app onto the Google Play Store as an installable Android app, reusing the existing web frontend. iOS App Store is explicitly deferred; iOS users get PWA install via Safari.

## Motivation & constraints

- Primary motivation: store presence and easy install for students. No native-feature requirements (push, widgets, offline sync) in v1.
- Android first; iOS later. No Mac/Apple Developer account needed now.
- The frontend + all three services are already hosted on a public HTTPS domain — a hard prerequisite for this approach, already satisfied.
- The frontend is a pure client-side SPA (no `use server`, no `next/headers`), auth via Bearer tokens in localStorage, all data over HTTP to auth/content/files services. Nothing structural changes.

## Chosen approach

**PWA + Trusted Web Activity (TWA), packaged with Bubblewrap.** Google's supported way to ship a web app on Play. The Android app is a ~1MB shell that renders the live site full-screen in Chrome, trusted via Digital Asset Links so no browser UI shows.

Rejected alternatives:

- **Capacitor wrap** — Next.js static export conflicts with the dynamic routes (`/topic/[id]`, `/chapter/[id]`, `/subject/[id]`, `/coaching/[groupId]/[userId]`); updates would require store releases. Revisit as the iOS path (its native-plugin access is what clears Apple guideline 4.2).
- **React Native / Expo rewrite** — weeks of duplicated frontend for a goal the TWA achieves in days. YAGNI.

## Architecture

```
Student's phone
└── Android TWA shell (~1MB .aab, generated by Bubblewrap)
    └── full-screen Chrome (no address bar, trusted via assetlinks.json)
        └── https://<domain>  — existing Next.js frontend + new PWA layer
            └── auth-service / content-service / files-service (unchanged)
```

- Backend, deployment, and auth flow are untouched. localStorage persists in the TWA's Chrome profile, so login sessions survive app restarts.
- Web deploys update the installed app instantly; Play re-review is only needed for shell changes.

## Component 1: PWA layer (`apps/frontend`)

- `app/manifest.ts` (Next.js manifest route): name, short_name, `display: "standalone"`, `start_url: "/"`, theme + background colors, icons.
- Icons: 512×512 master → 192/512 standard + **maskable** variants (required for Android adaptive icons); reused for the store listing.
- Service worker via **Serwist** (maintained next-pwa successor, Next 15 App Router compatible):
  - network-first for pages and API calls, cache-first for static assets
  - offline fallback page: "You're offline — revision data needs a connection"
  - deliberately minimal scope; no offline data sync in v1
- Viewport/theme-color metadata in `layout.tsx`; targeted mobile-polish fixes only where genuinely broken on phones (tap targets, safe-area insets). No redesign.

## Component 2: Android packaging (new top-level `android-twa/`)

- Generated by `@bubblewrap/cli` from the live manifest URL; the generated project is committed for reproducible builds.
- Signing: upload keystore generated locally, **kept out of git**; enroll in Play App Signing (mandatory). `assetlinks.json` must carry the **Play-provided signing key SHA-256**, not the upload key's.
- Output: `.aab` (Play requires App Bundles).
- `/.well-known/assetlinks.json` served from the domain root.

## Component 3: Play Store submission

| Item | Detail |
|---|---|
| Developer account | $25 one-time. Personal accounts must run a **closed test: ≥12 testers for 14 continuous days** before production access — the dominant schedule item |
| Store listing | Title ≤30 chars, short + full description, 2–8 phone screenshots, 1024×500 feature graphic, 512×512 icon |
| Privacy policy | Mandatory public URL (emails + user content are collected); small static page on the domain |
| Data safety form | Email (account management), user content (revision data), no third-party sharing |
| Content rating | IARC questionnaire → Education / Everyone |
| Target API level | Latest required by Play for new apps (API 35 at time of writing); Bubblewrap templates track this |
| **Account deletion** | Play requires an in-app delete-account path **and** a public web deletion URL. This is the one item touching the services: auth + content + files all need a real cascade-delete flow |
| assetlinks.json | Must match Play App Signing SHA-256, verified in closed testing |

## Error handling

- Offline → service-worker fallback page (never the Chrome dino).
- assetlinks mismatch → browser address bar appears inside the app (classic TWA failure mode); explicitly checked during closed testing.
- Domain/TLS outage → app is down exactly as the website is; no extra handling in v1.

## Testing

- Lighthouse PWA audit passes (installability, manifest, service worker).
- Existing vitest suite unchanged; add coverage for the offline fallback route if practical.
- Real-device closed-track checks: login persistence across restarts, deep links into `/topic/[id]`, Android back-button behavior, file upload from the phone camera/gallery.

## Deferred: iOS

- Shipping the PWA layer already gives Safari users "Add to Home Screen".
- When App Store presence matters: Capacitor shell reusing this PWA groundwork + Mac (or cloud-Mac CI) + $99/yr Apple Developer + enough native capability (typically push notifications) to pass Apple guideline 4.2 (minimum functionality).

## Cost & effort

- **Money:** $25 one-time (Play developer account).
- **Work:** PWA layer 1–2 days; Bubblewrap + signing ~0.5 day; store assets + forms ~0.5 day; account-deletion feature ~1 day (does not exist today).
- **Calendar:** ~3 weeks to public listing, dominated by the mandatory 14-day closed test.
